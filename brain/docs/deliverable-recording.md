# 成果物から判断理由・確認結果を辿る記録工程

この公開用コピーで成果物を作成・改訂する場合の記録工程。既存のProject / Memory / Canonical Context / Correction Logの役割・保存条件は変更しない。

## 達成する状態

完成物または配布入口 → 完成記録 → 重要な判断・理由・採用しなかった案 → 根拠と確認結果を辿れること。成果物の完成、本人受入、記録の整備、根拠の充足は別に判定する。記録が足りないから成果物を自動で未完成に戻したり、記録を書いたから本人受入済みにしたりしない。

## 途中で残すもの

方針確定、方針変更、失敗を受けた方法変更、受入条件変更、引渡し・中断の前に、後から知らないと再検討や再失敗につながる判断を案件の07_logs/decisions.mdへ短く記録する。全操作履歴や会話全文は保存しない。

判断ごとに、日付、決定主体（本人確認／実装者判断／未確定提案）、決定、理由、見送った案、根拠の所在、適用範囲・見直し条件を残す。不明な理由や比較していない代替案は「未確認／比較記録なし」とし、AIが補作しない。現在採用する方針はProjectのDecisions、詳細な経緯は判断ログを参照する。

## 完成・引渡し・中断の工程

1. 今回の意味ある完成単位を特定する。アプリだけでなく文書、帳票、設定、公開物も対象。雑談や単なるファイル整理は新しい成果物の完成としない。
2. 案件の07_logs/completions/YYYY-MM-DD-短い名称.mdを、brain/templates/completion-record.md.templateから作る。基盤共通の成果物はlogs/completions/を使える。元資料と成果物を移動・改変しない。
3. 「成果物と完成範囲」「判断と理由」「確認結果」「未確認・残件」「調査範囲と出典」を埋める。成果物は実在パス・版・変更範囲を明記し、判断・試験ごとに根拠を近接させる。
4. テストには対象版、実施日、実施環境、方法、結果、証跡、実施者を可能な範囲で記載する。自動テスト／実機確認／本人申告／過去の記録の再掲を区別する。未実施・未確認・失敗・対象外をPASSへ丸めない。
5. 配布READMEまたは成果物の案内ファイルに完成記録への逆向きリンクを付け、Projectには完成範囲・受入状態・記録への参照だけを残す。バイナリ成果物や保護対象の原本をリンク追加のために改変しない。
6. 下記の構造検査と、実際にリンクを辿る内容確認を行う。作業最終報告は「成果物／確認／記録／残件／外部反映」を分ける。通常のGit保存・外部操作の権限条件は従来どおり。

```powershell
python brain/tools/check_deliverable_records.py --record projects/対象/07_logs/completions/対象.md
python brain/tools/check_deliverable_records.py --record projects/対象/07_logs/completions/対象.md --strict
```

終了0は構造・参照先の存在についての合格。終了2は形式・参照の不備または対象なし。--strictで終了3なら調査途中または根拠不足。標準モードで0でも記録整備完了・実装正常とは限らない。--strictもメタデータ申告と構造の検査であって、本文の真偽や過去の判断の網羅性を証明しない。

成果物のパスから記録を逆引きできる。結果がpartial/gapsなら根拠不足を残す。見つからない場合の終了コードは4。ここでも内容の真偽を自動認定しない。

```powershell
python brain/tools/check_deliverable_records.py --lookup projects/対象/05_output/成果物名
```

## 記録の状態

review_stateはpartial（途中）またはreviewed（宣言した調査範囲を照合済み）。evidence_stateはgaps（必要な根拠不足）またはsufficient（宣言した完成単位の説明に必要な根拠が揃う）。両方を明記する。「調査済みだが当時の理由が記録にない」はreviewed/gapsであり、欠落を埋めたことにはしない。

originはcontemporaneous（作業時記録）またはretrospective（後日復元）。recorded_atは記録日、event_dateは実際の節目の日（不明ならunknown）。source_snapshotは照合したGitコミットの40桁SHAであり、過去の成果物の完成日やテスト版を代用しない。昔の版と現行版の一致を確認できなければ本文へ明記してgapsにする。

機械用traceブロックはこのMarkdown記録の一部であり、独立したMemoryデータベースではない。artifacts/sourcesのpathはリポジトリルートからの相対パス。sourcesは実際に読んだファイルだけを記載し、読んでいない候補は本文の未調査欄へ分ける。basisのhistorical-recordやuser-confirmation-recordは過去記録の根拠種別であり、今回の再実測・本人への再確認ではない。

## 過去分の補完を優先する

まずGit追跡対象の現在ファイル・アーカイブと、brain/projectsの案件を突き合わせて対象表を作る。フォルダ数、Project数、成果物数、旧版数を混同しない。最終配布セット、重要な改訂単位、実際の運用切替を一単位とし、全ての中間ファイルを独立した完成物にしない。

優先順は、完成・受入済みの成果物 → 重要な改訂・再受入 → 中断・不採用・未完成成果物。必要な場合だけ当該案件のREADME/manifest、Project、判断・検証文書、アーカイブ、Git履歴、参照された元資料へ遡る。archiveという名前だけで不採用や失敗と決めない。旧版を現行の方針へ昇格させない。

```powershell
# 本文は読まず、追跡済みoutput/archive内のファイル名から候補表を標準出力へ出す。
python brain/tools/check_deliverable_records.py --inventory
```

この候補表だけでは全体を網羅しない。コードのみの納品、Git管理外の資料、外部サービスにだけある成果物、削除済みGit履歴も別途確認する。本文未調査を「記録済み」と呼ばず、未調査／部分補完／照合済み・根拠不足／照合済み・根拠充足を区別する。

全件完了の条件は、合意した対象一覧の未調査が0で、各完成単位の成果物・判断理由・確認結果への参照を照合し、根拠不足が解消または本人に明示された残件として合意されていること。未知の対象範囲や未取得資料が残る場合は全件完了と報告しない。必要な理由・検証を復元不能なら、その事実と調査範囲・次の確認先を残す。原資料の欠落を後付けのAI説明で埋めない。

## 機密性・保存境界

会話全文、実業務データ、人名等の不要な詳細、秘密値を保存しない。Git管理外の証跡は存在と役割だけを説明し、無断でGitへコピーしない。既存資料が医学・法務等に関わる場合も、記録整理で正しさや適法性を新たに認定しない。元ファイルを再編集・再実行・再送信しない。

案件横断で再利用したい教訓は候補として整理するが、Memoryへの保存は本人の保存意思に従う。Canonical ContextやCorrection Logは本工程から自動更新しない。索引・完成記録からProjectの現在地を推測更新しない。

## 検査の限界

現在のチェッカーはテンプレートの必須項目・日付・状態・trace参照先・パス境界・未調査フラグを検査する。本文の全Markdownリンク、指定Git SHAの実在、全履歴・全成果物の網羅性、コードとテストの意味的一致は検査しない。入口からの逆参照と内容照合を人または担当AIが別途確認する。新しい検索DB、常駐エージェント、他リポジトリの導入は含めない。
